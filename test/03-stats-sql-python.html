Probability and statistics

S1

1% of transactions are fraudulent. A model flags 95% of fraud, and wrongly flags 5% of legitimate transactions. If a transaction is flagged, what's the probability it's actually fraud?

TestsBayes' theorem and base-rate reasoning. Almost guaranteed at a card company.

Answer

Let \(F\) be "fraud" and \(A\) be "flagged". We know \(P(F) = 0.01\), \(P(A \mid F) = 0.95\) and \(P(A \mid \neg F) = 0.05\).

\[ \begin{aligned} P(F \mid A) &= \frac{P(A \mid F)\,P(F)}{P(A \mid F)\,P(F) + P(A \mid \neg F)\,P(\neg F)} \\ &= \frac{0.95 \times 0.01}{0.95 \times 0.01 + 0.05 \times 0.99} = \frac{0.0095}{0.0590} \approx 0.16 \end{aligned} \]

Only about 16% of flags are real fraud. Because legitimate transactions outnumber fraud 99 to 1, even a 5% false alarm rate produces five times as many false alarms as true catches.

The practical implications: judge the model on precision at the chosen threshold, not on its 95% catch rate alone; use a second-stage review or step-up authentication rather than blocking outright; and remember that the base rate drives everything.

Quick sanity check

Picture 10,000 transactions: 100 are fraud, and 95 of those get flagged. Of the 9,900 legitimate ones, 495 get flagged. So 95 of the 590 flags are fraud, which is 16%.

S2

What is a p-value, and what is it not?

TestsThe single most misunderstood statistic.

Answer

The p-value is the probability, assuming the null hypothesis is true, of seeing a result at least as extreme as the one observed:

\[ p = P\big(T \ge t_{\text{observed}} \;\big|\; H_0\big) \]

A small p-value means the data would be surprising if there were no effect. If it falls below a threshold \(\alpha\) that you set in advance, commonly 0.05, you reject \(H_0\).

It is not:

  • the probability that \(H_0\) is true;
  • the probability that the result happened by chance;
  • a measure of how large or important the effect is. A tiny, useless effect can have \(p \lt 0.001\) with enough data.

Also watch multiple comparisons: test 20 variants at \(\alpha = 0.05\) and you expect one false positive by chance. Correct for it, for example with Bonferroni, which uses \(\alpha / m\) for \(m\) tests. Picking the best of several prompts by their test scores has the same problem.

S3

Explain Type I and Type II errors and statistical power, using fraud detection.

TestsLinking hypothesis-testing language to business costs.

Answer

Take \(H_0\) as "this transaction is legitimate".

  • A Type I error (false positive, rate \(\alpha\)) is flagging a legitimate transaction. The cost is a declined card, an annoyed customer and support calls.
  • A Type II error (false negative, rate \(\beta\)) is missing real fraud. The cost is direct financial loss.
  • Power \(= 1 - \beta\) is the probability of catching fraud when it's there. In model terms, that's recall.

For a fixed model you can't reduce both at once: lowering the flagging threshold catches more fraud (fewer Type II errors) but blocks more good customers (more Type I). The right threshold comes from comparing their costs. To reduce both, you need a better model or more information.

In experiment design, power depends on sample size, effect size and \(\alpha\). The convention is to aim for 80% power.

S4

What does a 95% confidence interval actually mean?

TestsA correct frequentist interpretation.

Answer

For a mean, the interval is

\[ \bar{x} \pm 1.96\,\frac{s}{\sqrt{n}} \]

where \(\bar{x}\) is the sample mean, \(s\) the sample standard deviation and \(n\) the sample size. The 95% describes the procedure: if you repeated the sampling many times and built an interval each time, about 95% of those intervals would contain the true mean.

It does not mean "there's a 95% probability the true value lies in this particular interval". The true value is fixed, and this interval either contains it or doesn't; that kind of probability statement needs a Bayesian credible interval.

Practically: a narrower interval means a more precise estimate, and it narrows with \(\sqrt{n}\), so halving its width takes four times the data. If a confidence interval for a difference excludes 0, the difference is significant at the matching level.

S5

What is the central limit theorem, and why does it matter?

TestsThe foundation of most everyday inference.

Answer

Take \(n\) independent samples from any distribution with mean \(\mu\) and finite variance \(\sigma^2\). For large enough \(n\), their average is approximately normally distributed:

\[ \bar{X}_n \;\approx\; \mathcal{N}\!\left(\mu,\ \frac{\sigma^2}{n}\right) \]

This holds even if the underlying data is heavily skewed, like transaction amounts. It matters because it justifies z-tests, t-tests and confidence intervals for means and proportions without knowing the data's actual distribution. It also gives the standard error, \(\sigma/\sqrt{n}\).

Example from my project: each ROUGE score was the mean of 100 per-article scores, so its standard error is the per-article standard deviation divided by 10. That's why differences of 0.01 between models aren't meaningful. Caveats: independence matters, and very heavy tails or small \(n\) slow the convergence.

S6

How would you design an A/B test for a new card-offer email? How many customers do you need?

TestsEnd-to-end experiment design, including a sample-size calculation.

Answer
  1. Define the metric and hypothesis in advance. For example, the primary metric is the offer acceptance rate within 14 days, with \(H_0\): no difference. Add guardrail metrics like unsubscribe rate.
  2. Choose the unit of randomization: the customer, not the email, so no one sees both versions. Randomly assign customers to control and treatment.
  3. Size the test for the smallest effect worth detecting (below).
  4. Run it for full weekly cycles, and don't stop early the moment it looks significant. Repeated peeking inflates false positives unless you use a sequential testing method.
  5. Check validity: confirm the groups really split as planned (a sample-ratio mismatch signals a bug) and that they're balanced on key covariates.
  6. Analyze with a two-proportion z-test and a confidence interval, and weigh statistical against practical significance.

Sample size per group for a baseline rate \(p\), a minimum detectable absolute lift \(\delta\), \(\alpha = 0.05\) (two-sided) and 80% power:

\[ \begin{aligned} n &\approx \frac{(z_{1-\alpha/2} + z_{1-\beta})^2 \cdot 2p(1-p)}{\delta^2} \\ &= \frac{(1.96 + 0.84)^2 \times 2 \times 0.05 \times 0.95}{0.01^2} = \frac{7.84 \times 0.095}{0.0001} \approx 7{,}450 \end{aligned} \]

With a 5% baseline and a 1-percentage-point lift to detect, that's about 7,450 customers per group. Halving the detectable lift roughly quadruples the requirement.

S7

When do you use a t-test, a chi-square test, or ANOVA?

TestsChoosing the right test for the data type.

Answer
  • t-test: compare the means of a continuous variable between two groups, such as average spend for customers with and without a reward. Use a paired t-test for before/after on the same customers, and Welch's version when variances differ.
  • ANOVA: compare means across three or more groups, such as spend across four card tiers. A significant result says some means differ; post-hoc tests (e.g. Tukey) say which.
  • Chi-square test of independence: check whether two categorical variables are related, such as card tier versus whether a customer defaulted, using a contingency table of counts.

If the data is heavily non-normal with small samples, non-parametric alternatives are Mann–Whitney U instead of the t-test and Kruskal–Wallis instead of ANOVA.

S8

Correlation isn't causation: give an example. What is Simpson's paradox?

TestsConfounding, and aggregation traps.

Answer

Premium card holders might have lower default rates. That doesn't mean giving someone a premium card makes them less likely to default: income and credit history drive both. That's a confounder. Establishing causation needs a randomized experiment, or careful causal methods such as matching or difference-in-differences, when experiments aren't possible.

Simpson's paradox is when a trend inside every subgroup reverses once the groups are combined, because the groups differ in size and composition. A classic medical example (kidney stone treatments):

Small stonesLarge stonesOverall
Treatment A81/87 = 93%192/263 = 73%273/350 = 78%
Treatment B234/270 = 87%55/80 = 69%289/350 = 83%

A is better for both stone sizes, yet B looks better overall, because A was mostly given to the harder large-stone cases. The lesson: check whether a confounding variable should be controlled before trusting an aggregate comparison.

S9

What is multicollinearity, and why does it matter?

TestsRegression diagnostics, common for credit-risk roles.

Answer

Multicollinearity is when predictors are strongly correlated with each other, such as credit limit, income and total spend. The model can't tell which one deserves the credit, so coefficient estimates become unstable. Their standard errors inflate, and signs can flip between samples, which ruins interpretation even though predictions may still be fine. It's measured with the variance inflation factor:

\[ \mathrm{VIF}_j = \frac{1}{1 - R_j^2} \]

Here \(R_j^2\) comes from regressing feature \(j\) on all the other features. A VIF above about 5–10 signals a problem. Fixes: drop or combine correlated features, use domain-based ratios (such as spend divided by limit), apply PCA, or use ridge regression, which stabilizes coefficients.

S10

Two quick ones: (a) Expected number of die rolls to get a six? (b) Each of 3 independent transactions is flagged with probability 10%. What's the probability at least one is flagged?

TestsFluency with expectation and complements.

Answer

(a) 6. Let \(E\) be the expected number of rolls. The first roll always counts, and with probability 5/6 it fails and you're back where you started:

\[ E = 1 + \tfrac{5}{6}E \;\Rightarrow\; \tfrac{1}{6}E = 1 \;\Rightarrow\; E = 6 \]

More generally, the expected wait for an event with probability \(p\) per trial is \(1/p\). This is the geometric distribution.

(b) 27.1%. Use the complement: "at least one" = 1 − "none".

\[ P(\text{at least one}) = 1 - (1 - 0.1)^3 = 1 - 0.729 = 0.271 \]
S11

What is the bootstrap, and how would you use it to compare two models?

TestsResampling-based inference, applied to your project.

Answer

The bootstrap estimates the uncertainty of a statistic by resampling your data with replacement. You treat the sample as a stand-in for the population, so no formula is needed.

Applied to my project, comparing fine-tuned T5-small (0.863 ROUGE-L) with zero-shot Flan-T5-large (0.875) on the same 100 articles:

  1. Save each model's score on every article, so each article has a pair of scores.
  2. Draw 100 article indices with replacement. For those articles, compute the difference in mean score between the two models.
  3. Repeat 10,000 times, giving 10,000 differences.
  4. The 2.5th and 97.5th percentiles of those differences form a 95% confidence interval. If it includes 0, the models aren't distinguishable on this test set.

Resampling the same articles for both models (a paired bootstrap) matters, because it removes the variation that comes from some articles simply being easier than others. I'd expect that interval to include 0, since the gap is about one article's worth.

Q12

What's the difference between WHERE and HAVING? In what order does SQL evaluate a query?

TestsThe mental model behind most SQL bugs.

Answer

WHERE filters rows before grouping, and HAVING filters groups after aggregation. So WHERE SUM(amount) > 10000 is invalid, and that condition belongs in HAVING. The logical evaluation order is:

FROM / JOIN → WHERE → GROUP BY → HAVING → SELECT (including window functions) → DISTINCT → ORDER BY → LIMIT

That order explains two common errors: you can't use a SELECT alias in WHERE, and you can't filter on a window function's result in WHERE. Wrap the query in a CTE or subquery and filter outside it.

SELECT customer_id, SUM(amount) AS total_spend
FROM transactions
WHERE txn_date >= DATE '2025-01-01'   -- row filter
GROUP BY customer_id
HAVING SUM(amount) > 10000            -- group filter
ORDER BY total_spend DESC;
Q13

Find customers with no transactions in the last 90 days, including customers who never transacted.

TestsJoin types, and the classic LEFT JOIN filter trap.

Answer 
SELECT c.customer_id
FROM customers c
LEFT JOIN transactions t
       ON t.customer_id = c.customer_id
      AND t.txn_date >= CURRENT_DATE - INTERVAL '90 days'   -- filter goes in ON
WHERE t.txn_id IS NULL;

A LEFT JOIN keeps every customer, with NULLs where no transaction matched, so t.txn_id IS NULL means "no recent transaction". The trap: putting the date condition in WHERE instead of ON discards the NULL rows before that check can see them. The query then silently behaves like an inner join and returns nothing useful. An equivalent that's often clearer:

SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM transactions t
  WHERE t.customer_id = c.customer_id
    AND t.txn_date >= CURRENT_DATE - INTERVAL '90 days'
);

Join types in one line each: INNER returns matches only, LEFT returns all left rows, RIGHT all right rows, FULL all rows from both, and CROSS every combination. Also watch for fan-out: joining one customer to many transactions before aggregating duplicates the customer-level values.

Q14

Find the second-highest transaction amount.

TestsSubqueries or ranking, and edge cases like ties and no second value.

Answer 
-- Option 1: subquery (returns NULL if there's no second distinct value)
SELECT MAX(amount) AS second_highest
FROM transactions
WHERE amount < (SELECT MAX(amount) FROM transactions);

-- Option 2: ranking (generalizes to the Nth highest)
SELECT DISTINCT amount
FROM (
  SELECT amount, DENSE_RANK() OVER (ORDER BY amount DESC) AS rnk
  FROM transactions
) ranked
WHERE rnk = 2;

Mention the edge cases: if the top amount appears twice, "second highest" should usually mean the next distinct value, which is why both options use distinct values rather than OFFSET 1. Option 1 returns NULL when only one distinct amount exists, and Option 2 returns no rows.

Q15

Find the top 3 customers by total spend in each city.

TestsWindow functions with PARTITION BY, and how ties are handled.

Answer 
WITH spend AS (
  SELECT c.city, t.customer_id, SUM(t.amount) AS total_spend
  FROM transactions t
  JOIN customers c ON c.customer_id = t.customer_id
  GROUP BY c.city, t.customer_id
),
ranked AS (
  SELECT city, customer_id, total_spend,
         DENSE_RANK() OVER (PARTITION BY city ORDER BY total_spend DESC) AS rnk
  FROM spend
)
SELECT city, customer_id, total_spend
FROM ranked
WHERE rnk <= 3
ORDER BY city, rnk;

Aggregate first, then rank within each city. Explain which ranking function you chose, using totals of 500, 500 and 300:

  • ROW_NUMBER gives 1, 2, 3: exactly three rows, with ties broken arbitrarily.
  • RANK gives 1, 1, 3: ties share a rank and the next rank is skipped.
  • DENSE_RANK gives 1, 1, 2: ties share a rank with no gaps.

Ask the interviewer whether tied customers should all be included.

Q16

Calculate month-over-month percentage growth in total spend.

TestsLAG, date truncation, and division edge cases.

Answer 
WITH monthly AS (
  SELECT DATE_TRUNC('month', txn_date) AS month,
         SUM(amount) AS spend
  FROM transactions
  GROUP BY 1
)
SELECT month,
       spend,
       LAG(spend) OVER (ORDER BY month) AS prev_spend,
       100.0 * (spend - LAG(spend) OVER (ORDER BY month))
             / NULLIF(LAG(spend) OVER (ORDER BY month), 0) AS pct_growth
FROM monthly
ORDER BY month;

LAG fetches the previous row's value in the given order. NULLIF(..., 0) avoids dividing by zero, and 100.0 forces decimal rather than integer division. The first month has no previous value, so its growth is NULL. Mention that months with no transactions at all won't appear, so for a gap-free series you'd join to a generated calendar of months.

Q17

Compute each customer's running total of spend over time.

TestsWindow frames.

Answer 
SELECT customer_id, txn_date, amount,
       SUM(amount) OVER (
         PARTITION BY customer_id
         ORDER BY txn_date, txn_id
         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_total
FROM transactions
ORDER BY customer_id, txn_date, txn_id;

The explicit ROWS frame matters. With only ORDER BY txn_date, the default frame treats all transactions on the same date as one peer group, so each of them would show the total including all of that day's transactions. Adding txn_id as a tie-breaker together with ROWS gives a true row-by-row running total.

Q18

Find duplicate transactions (same customer, amount and date), then delete the extras, keeping one.

TestsGROUP BY with HAVING, and ROW_NUMBER for de-duplication.

Answer 
-- Find them
SELECT customer_id, amount, txn_date, COUNT(*) AS copies
FROM transactions
GROUP BY customer_id, amount, txn_date
HAVING COUNT(*) > 1;

-- Delete extras, keeping the lowest txn_id in each group
WITH ranked AS (
  SELECT txn_id,
         ROW_NUMBER() OVER (
           PARTITION BY customer_id, amount, txn_date
           ORDER BY txn_id
         ) AS rn
  FROM transactions
)
DELETE FROM transactions
WHERE txn_id IN (SELECT txn_id FROM ranked WHERE rn > 1);

Before deleting, say you'd confirm these are truly duplicates. Two identical coffees on the same day are legitimate, so a real key would include a timestamp or merchant. And run the SELECT first, ideally inside a transaction.

Q19

Find customers who made transactions on at least 3 consecutive days.

TestsThe "gaps and islands" pattern, a common harder question.

Answer 
WITH days AS (
  SELECT DISTINCT customer_id, txn_date AS d
  FROM transactions
),
islands AS (
  SELECT customer_id, d,
         d - CAST(ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY d) AS INT) AS island
  FROM days
)
SELECT DISTINCT customer_id
FROM islands
GROUP BY customer_id, island
HAVING COUNT(*) >= 3;

The trick: number each customer's distinct active days in order. For consecutive dates, the date and the row number both go up by 1 each step, so date minus row number stays constant. A gap in dates changes that constant. Each constant value marks one run of consecutive days, and counting the rows per run finds runs of 3 or more:

DateRow numberDate − row number
Mar 11Feb 28
Mar 22Feb 28
Mar 33Feb 28 → run of 3
Mar 54Mar 1 → new run

The first CTE takes distinct dates so that several transactions on one day count as one day. (The example dates assume a non-leap year.)

When would you use a list, tuple, set or dict? What are the lookup costs?

TestsChoosing data structures by complexity.

Answer
TypePropertiesMembership testUse it for
listordered, mutable, duplicates allowedO(n)sequences you append to or index by position (append is O(1) amortized; inserting at the front is O(n))

P21

Given a list of numbers and a target, return the indices of two numbers that add up to the target, in O(n).

TestsUsing a hash map to trade memory for time.

Answer 
def two_sum(nums, target):
    seen = {}                      # value -> index
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:           # O(1) average lookup
            return seen[need], i
        seen[x] = i
    return None

two_sum([2, 7, 11, 15], 9)         # (0, 1)

The brute force checks every pair in O(n²). Storing values already seen in a dict means each number only needs one lookup for its complement, giving O(n) time and O(n) memory. Checking before inserting prevents pairing a number with itself. If the input is already sorted, two pointers moving inward from both ends find the pair in O(n) time with O(1) extra space.

P22

Implement ROUGE-1 F1 between a generated title and a reference.

TestsCoding a metric you used, correctly and with edge cases.

Answer 
from collections import Counter

def rouge1_f1(generated: str, reference: str) -> float:
    gen = generated.lower().split()
    ref = reference.lower().split()
    if not gen or not ref:
        return 0.0
    overlap = sum((Counter(gen) & Counter(ref)).values())   # clipped matches
    if overlap == 0:
        return 0.0
    precision = overlap / len(gen)
    recall = overlap / len(ref)
    return 2 * precision * recall / (precision + recall)

rouge1_f1("barrier reef coral reef", "great barrier reef")   # 0.571...

The key detail is Counter & Counter, which keeps the minimum count of each word. That implements ROUGE's clipping: "reef" appears twice in the generated title but once in the reference, so it matches only once. The early returns handle empty strings and no overlap, avoiding division by zero. The real rouge_score library also strips punctuation and can apply stemming.

P23

In pandas, flag transactions that are more than 3× a customer's usual spend.

Testsgroupby().transform, and thinking about how the baseline is defined.

Answer 
import pandas as pd

g = df.groupby("customer_id")["amount"]
total = g.transform("sum")
count = g.transform("count")

# mean of the customer's OTHER transactions (leave-one-out)
df["baseline"] = (total - df["amount"]) / (count - 1)
df["is_unusual"] = df["amount"] > 3 * df["baseline"]

transform returns a value aligned to every original row, unlike agg, which returns one row per group. Two design points are worth saying out loud:

  • Leave-one-out. A plain per-customer mean includes the transaction being judged, so a huge purchase inflates its own baseline and hides itself.
  • Customers with a single transaction get 0/0 = NaN, and NaN comparisons are False, so they're never flagged. Decide whether that's acceptable.

In production I'd use the median (robust to outliers) over a trailing time window of past transactions only, to avoid the leakage in M4.

P24

Why is vectorized NumPy or pandas code so much faster than a Python loop?

TestsUnderstanding performance, not just knowing it's true.

Answer 
import numpy as np
x = np.random.rand(1_000_000)

slow = sum(v * 2 for v in x)   # a million interpreter steps
fast = (x * 2).sum()           # two calls; the loops run in compiled C

A Python loop pays interpreter overhead for every element: dispatching each operation, checking types, and creating a new Python number object for every intermediate result. A vectorized operation makes one call into compiled C code that loops over a contiguous block of raw numbers of a single known type. That avoids all the per-element overhead, uses the CPU cache efficiently, and can use SIMD instructions that process several numbers at once. The speed-up is typically 10–100×. In pandas, .apply with a Python function is essentially a loop, so prefer built-in column operations.

P25

What is a generator, and when would you use one?

TestsMemory-efficient data processing.

Answer 
def read_articles(path):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.strip()      # produces one item, then pauses

for article in read_articles("articles.txt"):
    process(article)                # only one line is in memory at a time

A function containing yield returns a generator: an iterator that computes each value on demand and pauses between values instead of building a full list. Memory stays constant however large the input is, which is ideal for streaming large files, database cursors or data pipelines. The trade-off is that a generator can only be iterated once and doesn't support indexing. spaCy's nlp.pipe, which I used for preprocessing, is built this way: it takes an iterable and yields processed documents one batch at a time.

P26

What's wrong with this function?

def add_tag(tag, tags=[]):
    tags.append(tag)
    return tags

TestsA classic Python gotcha.

Answer

Default argument values are evaluated once, when the function is defined, not on each call. Every call that omits tags shares the same list, so it keeps growing:

add_tag("a")    # ['a']
add_tag("b")    # ['a', 'b']   <- surprise

The fix is to use None as the default and create a fresh list inside:

def add_tag(tag, tags=None):
    if tags is None:
        tags = []
    tags.append(tag)
    return tags

The same applies to any mutable default, such as dicts and sets.

P27

Threads or processes for speeding up Python work? What's the GIL?

TestsConcurrency basics, which matter for data engineering roles.

Answer

In standard CPython, the Global Interpreter Lock allows only one thread to execute Python bytecode at a time. So:

  • I/O-bound work (API calls, database queries, downloads): use threads or asyncio. Threads release the GIL while waiting, so they overlap usefully.
  • CPU-bound pure-Python work (parsing, feature computation in loops): use processes via multiprocessing or concurrent.futures.ProcessPoolExecutor. Each process has its own interpreter and GIL. The cost is start-up time and copying data between processes.
  • NumPy, pandas and PyTorch release the GIL inside their compiled code, so threads can parallelize those operations.

spaCy's n_process option uses multiple processes for exactly this reason. Python 3.13 also introduced an experimental build without the GIL, but the rules above still describe the standard interpreter.
